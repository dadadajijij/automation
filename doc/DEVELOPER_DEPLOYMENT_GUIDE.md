# 项目开发与自动化部署适配指南

本文说明项目在开发和交付时需要遵循的约定，帮助项目顺利接入自动化部署平台。

平台会分析源码、生成或复用部署文件、构建容器，并将服务发布到：

```text
https://<平台域名>/tools2/<项目标识>/
```

当前主要支持 Python、Node.js，以及 Next.js、Vite、Vue CLI、Create React App、Express 静态服务和常规静态页面。其他技术栈、多个独立服务或特殊运行环境，请提前与平台维护人员确认。

## 1. 交付一个可以独立构建的项目

项目应包含构建和运行所需的源码、依赖声明、配置模板及静态资源。

推荐结构：

```text
project/
├── README.md
├── .env.example
├── .gitignore
├── .dockerignore
├── package.json / pyproject.toml / requirements.txt
├── 对应的依赖锁文件
├── src/
└── public/ 或其他必要资源目录
```

请遵循以下要求：

- 从干净目录获取源码后，能够按照 README 完成依赖安装、构建和启动。
- 使用项目内声明的依赖，避免依赖开发者电脑上的全局工具和软件。
- 保留依赖锁文件，明确语言和包管理器版本。
- 避免引用项目目录之外的源码、配置或资源。
- 运行依赖模型、字典或其他大文件时，说明获取方式、版本和存放位置。
- 不要交付本地虚拟环境、`node_modules`、临时缓存和无关历史数据。
- 提交 Git 项目时，确认必要文件已经纳入版本管理。

上传压缩包时，请让目录层级清晰，避免多层重复嵌套。

## 2. 提供明确的构建和启动命令

平台需要识别“如何安装”“如何构建”“如何启动服务”。

### Node.js 项目

在 `package.json` 中提供清晰的脚本，例如：

```json
{
  "scripts": {
    "build": "tsc",
    "start": "node dist/server.js"
  }
}
```

请确保：

- `build` 可以非交互执行。
- `start` 启动正式服务，并以前台进程持续运行。
- 启动需要的构建产物能够由 `build` 生成。
- 正式运行所需依赖和资源不会在裁剪依赖时被移除。
- 使用 pnpm、yarn 或 workspace 时，在 README 中注明版本和操作位置。

前端项目请区分开发服务器、构建命令和部署后的服务方式。

### Python 项目

提供 `pyproject.toml` 或 `requirements.txt`，并明确 Python 版本与入口命令。

例如：

```bash
python -m my_project
```

或：

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8080
```

请确保：

- 入口模块、应用对象和工作目录明确。
- 依赖安装过程不要求人工输入。
- 不依赖本地 `.venv` 或开发机器的绝对路径。
- 不在每次启动时重复执行耗时安装。

## 3. 使用明确、可配置的服务端口

容器内服务应监听：

```text
0.0.0.0:<服务端口>
```

只监听 `127.0.0.1` 可能导致容器外无法访问。

建议通过 `PORT` 环境变量配置端口，并提供明确默认值：

```javascript
const port = Number(process.env.PORT || 8080);
app.listen(port, "0.0.0.0");
```

请在 README 中注明：

- 默认端口。
- 修改端口的方法。
- 健康检查路径。

避免使用随机端口或开发机器专用 IP。已有平台项目的端口调整，需要同时通知平台维护人员更新映射配置。

## 4. 前端必须支持部署在子路径下

平台部署入口为：

```text
/tools2/<项目标识>/
```

这是适配时最需要关注的约定。

### 4.1 统一管理应用基础路径

请通过框架配置或统一路径工具管理部署基础路径，避免在业务代码中分散拼接。

常见配置包括：

| 框架 | 需要关注的配置 |
|---|---|
| Next.js | `basePath`，按需配置 `assetPrefix` |
| Vite | `base` |
| Vue CLI | `publicPath` |
| Create React App | `homepage` |
| 前端路由库 | 路由基础路径，如 `basename` 或 history base |

部分框架的基础路径在构建时确定，需要使用目标部署路径重新构建。

### 4.2 检查浏览器侧的根路径引用

以下写法会访问域名根目录，需要结合部署基础路径调整：

```javascript
fetch("/api/tasks");
window.location.href = "/login";
```

```html
<script src="/assets/app.js"></script>
<a href="/download/result.csv">下载</a>
<form action="/api/upload"></form>
```

建议统一提供：

- 应用内 API 地址生成方法。
- 应用内跳转方法。
- 静态资源路径配置。
- 上传、下载和实时连接地址配置。

相对路径也需要结合页面层级和路由规则验证；只去掉开头的 `/` 不能保证正确。

### 4.3 覆盖完整的路径使用场景

除首页外，还需要检查：

- API 请求。
- 图片、字体、脚本和样式。
- 页面跳转和登录重定向。
- 深层路由直接访问及刷新。
- 上传表单和下载地址。
- 懒加载资源。
- SSE、WebSocket。
- 后端返回给浏览器的链接及重定向地址。

访问其他系统的外部 URL 应单独配置，避免与应用自身路径混用。

平台提供自动适配，但复杂或动态生成的路径仍需要开发者主动处理。

## 5. 使用环境变量管理配置和密钥

运行环境差异应通过配置表达，例如：

```dotenv
PORT=8080
DATABASE_URL=
API_BASE_URL=
API_KEY=
DATA_DIR=/app/data
```

请提供 `.env.example`，仅包含变量名、示例值和必要说明。

每个变量应说明：

| 字段 | 说明 |
|---|---|
| 名称 | 环境变量名称 |
| 用途 | 控制什么功能 |
| 是否必填 | 缺失是否影响启动或业务 |
| 默认值 | 如无默认值，明确注明 |
| 生效阶段 | 构建时或运行时 |

请遵循以下要求：

- 不在源码、Dockerfile、README 或前端代码中写入真实密钥。
- 将真实 `.env` 排除在 Git 和镜像构建上下文之外。
- 不在日志中输出密钥、完整连接串或完整环境变量。
- 必填配置缺失时，给出明确错误。
- 前端打包变量可能对浏览器公开，不能用于保存服务端密钥。

## 6. 明确持久化数据目录

容器可能被删除和重建。需要保留的数据应写入明确、可挂载的目录。

推荐集中管理，例如：

```text
/app/data       数据库、业务状态
/app/uploads    上传文件
/app/output     需要保留的处理结果
```

请在 README 中说明：

- 哪些目录需要持久化。
- 数据用途及是否允许清理。
- 所需读写权限。
- 是否需要初始数据。
- 备份、恢复和版本迁移要求。

避免将重要数据写入随机临时目录或散落在源码目录中。

**声明了数据目录后，仍需要由平台配置卷挂载；平台识别到目录不代表已经完成持久化。**

## 7. 提供可用于验收的健康检查

建议提供：

```text
GET /health
```

服务可正常处理请求时返回：

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{"status":"ok"}
```

建议满足：

- 无需登录。
- 响应轻量、快速。
- 不产生业务写入。
- 不返回敏感信息。
- 服务尚未就绪时返回明确的失败状态，例如 `503`。
- 核心依赖不可用、导致服务无法工作时，能够反映异常。

请在 README 中注明路径，以及该接口检查哪些条件。

当前平台的启动检查较宽松，因此项目仍应提供真实有效的健康接口和业务验收方法。

## 8. 明确外部服务与系统依赖

项目如果依赖以下组件，请完整说明：

- 数据库、Redis、对象存储。
- 第三方 API。
- ffmpeg、sqlite3、浏览器等系统工具。
- 模型文件、GPU 或其他硬件。
- 内网连接、代理或特定网络权限。

每项依赖应说明：

- 用途和版本要求。
- 配置方式。
- 初始化步骤。
- 不可用时的行为。

不要默认容器可以访问开发者电脑上的 `localhost` 服务。

数据库建表、迁移、创建管理员等操作，请提供明确命令，并说明是否支持重复执行。

当前流水线主要围绕单个应用容器运行；需要多个独立容器时，请提前确认部署方案。

## 9. Dockerfile 可以提供，也可以由平台生成

平台可以生成 Dockerfile；已有 Dockerfile 时，请确保它适用于当前源码。

建议：

- 基础镜像版本明确。
- 依赖安装和构建能够非交互执行。
- 包含实际需要的系统工具和静态资源。
- 使用 JSON 形式的启动指令：

```dockerfile
CMD ["node", "dist/server.js"]
```

或：

```dockerfile
CMD ["python", "-m", "my_project"]
```

- 多阶段构建的最终镜像包含全部运行依赖。
- 提供合理的 `.dockerignore`，排除密钥、本地依赖、缓存和无关数据。
- 程序能处理停止信号，正常退出并保存必要状态。

源码入口、依赖或运行环境变化时，应同步更新 Dockerfile。

## 10. README 中至少提供这些信息

建议包含：

```markdown
# 项目名称

## 项目用途
项目解决什么问题，以及一个核心使用场景。

## 运行环境
语言版本、包管理器版本、系统工具要求。

## 安装与构建
依赖安装命令、构建命令及执行目录。

## 启动
启动命令、监听地址、默认端口。

## 环境变量
变量名、用途、必填项、默认值、生效阶段。

## 外部依赖
数据库、缓存、第三方 API、初始化和迁移命令。

## 数据存储
持久化目录、权限、备份和恢复要求。

## 部署路径
子路径配置方法、前端路由及 API 地址配置。

## 健康检查
路径、正常响应及检查范围。

## 验收步骤
能够验证核心功能的操作步骤和预期结果。

## 升级注意事项
数据兼容性、迁移步骤、回滚限制。
```

复杂 monorepo 还应注明实际部署的服务包、前端目录和构建输出位置。

## 11. 复杂项目可以提供子路径声明

平台支持通过 `.ka/subpath.json` 显式声明前端结构，减少自动识别误差。

示例：

```json
{
  "projects": [
    {
      "root": "frontend",
      "framework": "vite",
      "proxy_mode": "preserve_prefix",
      "config_file": "frontend/vite.config.ts",
      "source_roots": ["frontend/src"],
      "runtime_roots": ["frontend/dist"]
    }
  ]
}
```

路径均相对于仓库根目录。

代理模式含义：

- `preserve_prefix`：应用接收并理解 `/tools2/<项目标识>` 前缀。
- `strip_prefix`：平台转发时移除前缀，后端按根路径提供服务；浏览器侧仍需要生成正确的子路径 URL。

上例仅用于说明格式。实际模式应结合服务如何提供页面、静态资源和 API 确定，建议与平台维护人员一起确认。
